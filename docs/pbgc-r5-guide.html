1. Purpose

The repository makes one product: the R5 Plan Summary. The R5 is a Word document. It lists the provisions of a terminated pension plan. Each provision has a value and a citation.

The office computer has no server, no Node, and no Python. The product is therefore one HTML file. The file is r5-generator.html. A user opens it with a double-click. It works offline.

WarningDo not give apps/r5-gui to an office user. It is a Vite and React reference only. It does not meet the office constraint.

3. Rules that shape the code

  1. The office app is one HTML file. It has no build step, no fetch(), no CDN, and no ES modules.
  2. The generator is deterministic. No language model runs in the calculation or generation path.
  3. A human approves each item. Review is a gate.
  4. The shell has three document columns. Documents 4 to 6 go in a repeated block below. Then 7 to 9, and so on.
  5. The header rates come from the BCV add-in functions, with provenance. The app never types a rate.
  6. A missing value is safer than a wrong value. The scraper never guesses.
  7. Development data is synthetic. The repository holds no real case data.
NoteThe file carries a Content-Security-Policy with connect-src 'none'. The page cannot open a network connection.

4. Workflow

The user moves through five steps. The app locks a step until the step before it is complete.

Draft and final

The user can make a draft at any time after the header and review are done. The final gate never blocks a draft. A final needs a clean gate. Any edit reopens a final to draft.

5. How the single file is built

The source lives in separate files. The script scripts/build_single_file.py copies them into the HTML. The HTML has one <script>. The script replaces named regions. It does not touch the app code.

CautionPut a new region after the line that holds compromise.js. A region placed before it drops the library from the build. The script docstring records this past defect.

6. Data model

All data moves as one JSON object: R5Json. The schema is schema/r5.schema.json. The TypeScript types are in types.ts.

Each of the 61 fields holds a list of answers. The list has one answer per document column. Index 0 is D1.

Rules in the types

  • An unknown date is null. The code never makes up a date.
  • An N/A needs a documented basis. Silence in an amendment is never N/A.
  • A document-search N/A needs readComplete: true on the source document.
  • A PDF page is trusted only when the page tree verified it.
  • The case number is exactly 8 digits. It is text, so leading zeros stay.

7. Scrape

The Scrape step runs runScraper() in the HTML. The function calls the pipeline in a fixed order. No step uses a network or a language model.

What the scraper does

  1. extract.js reads text. It reads .docx as a ZIP and .pdf with a minimal extractor. It has no OCR.
  2. scrape.js splits the text into sentences. Each sentence keeps its plan section.
  3. Regular expressions and compromise.js patterns propose one STE 100 value per item.
  4. No match gives missing. Two conflicting values give ambiguous. An explicit "no such provision" sentence gives notApplicable.
  5. Each present value gets a citation code and an audit entry.

How the app orders documents

ordering.js applies the plan-summary rules. D1 is the oldest full plan document in effect at least five years before the earlier of BPD and DOPT. Later columns are amendments with significant changes. Minor amendments go in footnotes. The function never sorts silently. If a date is unknown, it asks for confirmation.

NoteAn uncertain amendment keeps a column. It blocks final until the reviewer confirms it.

8. Reconcile across documents

reconcileProvision compares one provision across the document columns, oldest first. It assigns a lifecycle to each answer. An amendment that is silent carries the earlier rule forward.

  • The first document that states a rule sets the governing rule.
  • A later document with a different rule is amended. The earlier answers become superseded.
  • A document that was not read never carries a rule into its column.
  • An ambiguous answer never changes the governing rule.

In the generated .docx, a cell that repeats the previous document shows same plus its own citation. The first column of each block always shows the full value.

9. Review and the final gate

Each pair has a review decision. An edit resets the pair to pending. "Approve all" is safe: it skips missing, ambiguous and incomplete pairs. It records whether an approval was bulk or explicit.

What blocks final

finalBlockers() in generate.ts lists every block. The HTML carries the same gate.

CheckBlocks when
HeaderPlan name, case number or DOPT is missing. The case number is not 8 digits.
Each pairThe pair is not approved. A missing or ambiguous pair has no explicit approval. A citation is incomplete.
N/ANo documented basis. Or the source document is not confirmed read in full.
DatesA date has a conflict. Or its meaning is not confirmed.
AmendmentsThe materiality of an amendment is uncertain.
RatesImported rates are stale, or their inputs were not recorded.

10. Header rates

The app cannot calculate the PBGC rates. The functions PPALSRATE, RATETIER and SPARR run only in Excel with the ATPBGC add-in. The app does a round trip instead.

  1. The app downloads the rates workbook, pre-filled with DOPT, stability period, lookback, anniversary, NOIT and NOD.
  2. The user opens it in Excel. The add-in calculates the Outputs. The user saves the file.
  3. The user uploads the saved file to the app.
  4. The app checks the file. It needs formulas, cached values and a lookup date on the first day of the month after DOPT.
  5. The app accepts SPARR only when the TID Status reads OK.
  6. The app fills the header rates and prints one provenance line per function.
CautionA header edit that changes a rate input clears the imported rates. It also reopens a final to draft.

12. Checks

Two layers test the work. The README reports the results for version 0.11.3. I did not run them for this guide.

  • Unit tests. npm test runs the vitest suites in the workspaces. The README reports 613 passing tests.
  • Harnesses. The scripts/verify_* files run the HTML's own inlined code in Node or Python. They check extraction, the actuarial fixtures, the end-to-end flow, the .docx output and the review gate.
  • Office test. The 15-step checklist in docs/OFFICE_CHECKLIST.md covers the Edge file:// load and the .docx in Word.

13. Limits

  • The app has no OCR. A scanned image-only PDF returns almost no text. OCR it first, or paste the text.
  • The app does not calculate the rates. Excel with the add-in does.
  • The README marks 0.11.3 as an office acceptance candidate. Office verification is still open.
  • apps/r5-gui no longer type-checks against the current schema.
  • Nine fields have no sourced R1 placement in the contribution export.
WarningDo not upload real PBGC documents to an unrestricted external language model.

14. Reading order

Use this order to learn the code.

  1. Read README.md from the top to "What it does".
  2. Read docs/STE100_STYLE.md. It shows the value and citation style.
  3. Read types.ts. It defines every shape.
  4. Read pipeline.js, then reconcileProvision in review.ts.
  5. Read finalBlockers in generate.ts.
  6. Read docs/TEMPLATE_FILL.md and templateFill.js.
  7. Read runScraper in r5-generator.html.
  8. Read scripts/build_single_file.py.

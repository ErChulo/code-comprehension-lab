SAMPLE: Defending pbgc-r5-generator

Why it exists, how it is built, and why each decision holds

repo pbgc-r5-generator  |  map built from 4da03b5  |  2026-11-22

The root problem

A reviewer must summarize a plan's provisions across many plan documents and amendments into one R5 table, and must be able to prove where every value came from.

Everything else follows from this problem.

The 5 decisions

  1. D1 Keep one answer per provision per document
  2. D2 Carry the governing rule forward when an amendment is silent
  3. D3 A missing value is safer than a guessed value
  4. D4 A final gate before publication
  5. D5 One self-contained file with no network

D1 Keep one answer per provision per document

Problem

Amendments change some provisions and say nothing about others. The summary must show what each document says.

What exists at this point

A list of plan documents in date order, and a list of provisions to summarize.

Why the obvious design fails

  1. A reader must see which document each value came frombreaks: one merged value per provision
  2. A later document may change a valuebreaks: keeping only the newest value

Options considered

OptionTrade-off
One merged valuesimple, loses history
Per-document answersmore data, keeps the trail
Event log of changescomplete, hard to read

The decision

Per-document answer table. Each provision holds one answer for each document column, in document order.

Where it lives in the code

packages/module-1-r5/src/types.ts::ProvisionAnswerone answer with value, citation and lifecycle
packages/module-1-r5/src/types.ts::R5Jsonholds provisions per field and per document

Evidence: code only

Data model

One ProvisionAnswer per provision per document.

D2 Carry the governing rule forward when an amendment is silent

Problem

An amendment says nothing about a provision. The old rule still applies. The table must not show a blank.

What exists at this point

Per-document answers (D1).

YOUR SESSION LOG (private, do not read aloud): struggled with: first said blank is safest; moved when asked what the reader sees found on their own: silence is not a change did well: named the trace requirement

D2 in plain words

Think of a rulebook with amendments. An amendment that does not mention a page does not remove the page.

So when a document is silent, the old rule still governs. The table shows that rule and says which document it came from.

Why the obvious design fails

  1. Silence is not a changebreaks: marking the cell missing
  2. Silence is not proof that no provision existsbreaks: marking the cell not applicable
  3. A later amendment may replace the rulebreaks: carrying the first value forever

Options considered

OptionTrade-off
Leave blankhonest, but hides the rule that governs
Copy value silentlylooks complete, hides the source
Carry forward with a tracecomplete and checkable

The decision

Lifecycle states (unchanged, amended, superseded, missing, notApplicable) and a carried-forward trace that names the source document.

Where it lives in the code

packages/module-1-r5/src/review.ts::reconcileProvisionwalks documents in order and tracks the governing rule
packages/module-1-r5/src/types.ts::CarriedForwardnames the document the value came from

Evidence: code only

D3 A missing value is safer than a guessed value

Problem

The extractor may not find a value. A wrong value in a regulatory filing costs more than a blank.

What exists at this point

Extraction results with a status.

Why the obvious design fails

  1. Do not guessbreaks: filling with the most likely value
  2. Not applicable needs proofbreaks: treating "not found" as "does not exist"

Options considered

OptionTrade-off
Trust the extractorfast, unsafe
Require evidenceslower, defensible

The decision

Not applicable only with affirmative evidence: a quoted sentence, or a full-document search on a full plan document.

Where it lives in the code

packages/module-1-r5/src/review.ts::hasAffirmativeAbsenceEvidencetests the evidence rule
packages/module-1-r5/src/types.ts::NaBasisrecords the basis for not applicable

Evidence: code only

D4 A final gate before publication

Problem

A draft with unresolved items must not leave the tool as a final document.

What exists at this point

Reviewed answers and approvals.

Why the obvious design fails

  1. Any edit invalidates earlier approvalbreaks: approving once and editing freely
  2. Case number must be exactly 8 digitsbreaks: free-text case numbers

Options considered

OptionTrade-off
Warn onlyeasy, ignored
Hard gateblocks until blockers are clear

The decision

Draft and final states. Only the publish step can set final. Any edit reopens draft.

Where it lives in the code

packages/module-1-r5/src/generate.ts::finalBlockerslists every reason to block
packages/module-1-r5/src/generate.ts::publishFinalsets final only when no blockers
packages/module-1-r5/src/generate.ts::reopenDraftreturns to draft

Evidence: code only

Document status

Only publishFinal sets final. Any edit reopens draft.

D5 One self-contained file with no network

Problem

The tool runs where there is no server and no network. Plan documents are sensitive.

What exists at this point

A set of source modules.

Why the obvious design fails

  1. No runtime networkbreaks: loading libraries from a CDN
  2. Easy to deliverbreaks: a folder of files

Options considered

OptionTrade-off
Hosted appeasy updates, needs network
Installed appneeds install rights
Single fileruns anywhere

The decision

Build step joins modules into one HTML file. A content security policy blocks all connections.

Where it lives in the code

scripts/build_single_file.py::mainjoins modules into one file
r5-generator.html::Content-Security-Policyconnect-src 'none'

Evidence: code only
